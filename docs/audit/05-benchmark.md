# 05 — Map UX & Rendering Benchmark

**Date:** 2026-10-02  
**Scope:** Benchmark for the production public directory map (Leaflet), using the map behavior and mobile UX audits as the current-state evidence.  
**Method:** Current official platform/SDK documentation, Apple HIG, Material Design bottom-sheet guidance, WCAG 2.2 and Nielsen Norman Group research. Product UI observations below are stated only where a first-party source documents them; recommendations are tailored to a local Arabic-language directory, not treated as a mandate to copy another product. No application code was changed.

## Benchmark

| Pattern | Industry standard | Why it works | Our current state (audit IDs) | Gap | Recommendation | Trade-off |
|---|---|---|---|---|---|---|
| Marker detail by zoom; cluster overlap | Apple Maps HIG says to cluster overlapping POIs and progressively reveal individual points as users zoom in; detail should also increase with zoom. Google Maps offers a MarkerClusterer with customizable rendering/algorithm. Leaflet.markercluster supports cluster bounds zoom, spiderfy at max zoom, and removal of offscreen markers for performance. | Keeps dense overview legible while retaining a clear way to reach individual records; one stable progression makes zoom predictable. | Production already uses 58 px plus 100 m grouping, numbered clusters, zoom-to-bounds/member chooser, compact dots/cards and larger local cards. However zone eligibility changes at zoom 15, renderer LOD at 15.5, and selected-zone + overview styling can disagree. Filtered results are memoized without zoom/viewport revision (BHV-01; UXM-07). | The key gap is not absence of clustering: separate functions implement eligibility, cluster grouping, collision suppression and LOD with overlapping thresholds. That can retain stale eligibility across the 15/15.5 boundary; local hit dimensions also vary. | Keep the existing multi-level cards and cluster interaction, but specify one zoom-state table and shared settled-camera input for eligibility, culling, LOD and cluster recomputation. Test crossings at 15 and 15.5 with and without selected zone; preserve the member chooser for coincident points/max zoom. | Unifying rules requires careful regression coverage around useful overview cards and selected businesses. Clusters trade immediate individual names for overview readability; chooser adds one tap in dense blocks. |
| Pan and “search this area” vs automatic refetch | Google’s current Maps JS docs expose viewport bounds and recommend bounds-aware search/restriction; its current place autocomplete docs explicitly update `locationRestriction` from `bounds_changed`. These are developer patterns, not a claim that Google consumer Maps always presents a particular “Search this area” button. Airbnb documents that moving/zooming the map reveals additional listings. No authoritative product source found in this pass establishes one universal consumer standard between a button and automatic fetching. | A deliberate search-area action gives people control over query timing and avoids results changing mid-pan. Automatic refresh can feel continuous when results are local, cached and quick. | Current browse pins are culled/updated for viewport after pan; there is no location/network refetch and no explicit “search this area” step in the reviewed production flow (I09–I10; BHV-04, see report §6). | Users cannot infer whether a pan only changes visible pins or asks for a new dataset; future backend-backed search could make this ambiguous. | Keep local in-memory results responsive on each settled pan. If/when server queries are added, debounce the settled bounds and show a clear “ابحث في هذه المنطقة” affordance only when the viewport changed materially; keep the prior results until user commits, then show loading/count. | An extra tap for network search; automatic fetch is faster for light/cached results but risks surprise, request churn and abrupt result changes. Avoid adding a button while all data is local and already loaded. |
| Map search, suggestions, and result context | Apple HIG recommends immediate/as-you-type search where possible, useful suggestions, a clear statement of search scope, and clear empty states. Google Place Search separates text search and nearby search and supports location restriction/bias; its examples list selectable results and map markers. Airbnb’s official help describes destination, landmark and neighborhood search, filters, map exploration, and grouped list/map results; its help also notes map listings may differ from list ordering to explain geographic distribution. | Scope and suggestions lower typing effort; list results carry richer text, while pins communicate location. Keeping these contexts connected makes a selected result easier to understand. | Local Arabic autocomplete is observed, capped to five business suggestions with category actions; no-results copy is shown. Choosing a suggestion clears query and leaves only selected marker/drawer when category is “all” (BHV-02, UXM-03, UXM-06). Queries omit selected zone, so selecting an outside-zone suggestion can be immediately cleared (BHV-03). | Search looks like a suggestion picker more than a persistent results mode; clearing the query also drops the surrounding search context. Filter scope is not consistently reflected in candidates. | Preserve current quick suggestions and Arabic category search. Keep the submitted query/scope visible as a removable token/chip after selection; scope suggestions consistently to the selected zone or visibly offer “search all areas.” Keep a small list/tray synchronized with the map on mobile, and identify when map pins represent geography while list ordering follows relevance. | Persistent context uses vertical space and needs explicit clear semantics. A full list can compete with the map; a compact expandable tray is a compromise. Expanding search to geocoding/remote POIs has data/licensing and ranking costs, so keep this directory’s business search focused unless broader place search is a product goal. |
| Search this area; selection persistence | Apple recommends a selected map element be visually distinct and place cards keep the selected location visible; Google’s APIs support viewport-bound search. These imply maintaining the selected item and search context through camera changes where the item remains valid, while refreshing its screen position. | People can pan to orient themselves without losing what they chose; explicit “clear selection” remains understandable. | Selected business is isolated from background clusters and survives zoom/pan in code, but may move out of view. Query selection clears the query and surrounding candidates. Filter change clears selection when category/zone no longer matches. (I11, I17, I22; BHV-02/03.) A compact selected marker plus bottom drawer are both displayed (UXM-06, observed). | Persistence semantics are split: underlying selection persists, but its context disappears; selected detail is duplicated and crowds short phones. | Retain valid selection across zoom and pan; keep its pin distinct and re-anchor/reveal it when opening details. Keep selected result in a compact bottom card/tray with one primary detail surface; show an explicit dismiss/clear action. If a changed filter excludes it, explain that it is outside the current filter and offer clear or broaden-scope rather than silently dropping it. | Keeping an out-of-filter selection can confuse result counts, so label it separately and exclude it from filtered count. A persistent card consumes map area; use collapsed/expanded states, not disappearance. |
| Mobile filter controls, chips, counts, apply state | NN/g recommends mobile filter trays that preserve visibility of results and immediate feedback; where users have several known criteria and network refresh is costly, batch apply is useful. Apple recommends visible search scopes/tokens that clarify current scope. WCAG 2.2 AA 2.5.8 minimum target is 24×24 CSS px or spacing exception; 44×44 is the enhanced AAA target, useful as a touch design goal, not AA’s universal minimum. | Active chips expose current constraints and make reversal cheap; counts reveal whether filters narrowed to zero; batch apply prevents each selection from causing a slow refresh. | Active category/zone is represented only by a small amber dot in collapsed toolbar; selected names are not visible as chips; count appears only after category selection. At 360×640 the filter footer is partly behind bottom nav (UXM-01, UXM-05). | Hidden applied state, incomplete count feedback, and obstructed footer reduce confidence and make recovery costly. | Show applied category and zone as removable chips (or compact “2 filters” with an accessible summary) beside search. Put result count and zero-result status in the filter sheet header and its sticky apply footer; offer reset. Keep draft vs applied distinction only if filters are committed in batch; otherwise reflect each live update immediately. Size/space controls for clear tapping, and reserve footer above nav/safe area. | Chips consume precious width on narrow Arabic RTL screens; collapse to count + summary when crowded. Live filtering gives fast feedback with local data but may visibly churn pins; batch filtering delays feedback yet avoids repeated refetch. Pick by measured latency. |
| Bottom sheet / drawer behavior | Apple HIG distinguishes modal and nonmodal sheets; nonmodal sheets let users act on the parent context. Material’s standard sheet remains visible beside the main region; modal sheets are dismissed to interact with the map; expanding sheets use a collapsed state, then internal scrolling, with care around bottom navigation and keyboard. Apple Maps presents place cards as callout or sheet based on context/device and advises avoiding duplicate content and keeping the selected location visible. | A sheet supports detail/filter tasks without forcing navigation away from map; snap states preserve map context while controlling obstruction. | Filter panel is an absolute dropdown rather than a sheet; the 360×640 view overlaps its bottom actions with navigation (UXM-01). Selected business uses a bottom drawer plus map card. Other building/navigation drawers lack explicit drag/snap and use `vh` without safe-area accommodation; device-specific clipping is suspected (UXM-06, UXM-10). | There is no single mobile overlay model; simultaneous bottom nav, filter panel and detail drawer compete for the same small viewport. | Use a compact nonmodal/expanding result sheet for map+list/detail, collapsed by default, expandable to internal-scroll full results. Use a modal filter sheet when criteria require a commit step, with sticky count/apply/reset and close/cancel semantics. On short screens hide or subordinate bottom nav while the sheet is expanded; account for safe areas and visual viewport. Keep desktop/tablet as side panel where space permits. | Sheet gestures need accessible explicit controls and can hide map area; modal filtering adds an apply step. Retrofitting a unified sheet model is broader than styling and should preserve existing actions and navigation. |
| Map/list interaction (Airbnb-style) | Airbnb’s current help says users can pan/zoom to find additional listings and use filters; its search help describes map and list as complementary, while noting map distribution may not exactly mirror list order. NN/g’s mobile locator research says a list-first default with an option to toggle map can be easier for choosing locations because lists carry more information density. | List gives names, distance, hours and actions; map gives orientation and proximity. Selection synchronization lets users switch representations without losing their place. | Production route is map-centric; selected-result card exists, but no persistent synchronized result list/tray on the public map path (UXM-03, UXM-06). `directory-experience` has a separate tray but is preview/test-routed and not evidence of production behavior (UXM-15). | A user who cannot identify a small/colliding pin has little text-first recovery on mobile. | Keep map as primary for the local neighborhood exploration task, but add a compact “النتائج” tray/list toggle rather than defaulting every visitor to list. Selecting a row highlights/re-centers its pin; selecting a pin highlights/scrolls its row; preserve scroll position and filters. | A list toggle and synchronization introduce state to maintain and reduce visible map area. NN/g’s list-first recommendation comes from location finders, so validate against this app’s map-as-core discovery purpose before making list the default. |
| Rendering model: Leaflet DOM markers vs data layers | Mapbox’s official guide says DOM markers are quick and highly customizable but less efficient at large counts (guide gives 100+ as a concern); style layers are better for large/complex data and can handle tens of thousands, with more complex interaction. Mapbox recommends clustering dense point sources at low zoom. Google recommends marker clustering to clean up large marker sets. Leaflet’s MarkerCluster plugin includes offscreen removal and cluster interaction defaults. | Rendering data in batches/layers reduces DOM pressure; DOM markers remain valuable for rich individually interactive cards and small selected sets. | Production builds custom Leaflet `divIcon`/marker cards, one group per feature, viewport culling and progressive insertion (BHV report §4; UXM-07, UXM-13). Group cache likely misses due to newly filtered array identity; performance risk is unmeasured (BHV §4). | Rich DOM cards are appropriate for a limited visible set, but broad candidate sets and custom grouping add independent reconciliation and invalidation paths. No measured frame-time evidence establishes a need to replace Leaflet or all DOM markers. | Preserve DOM markers for selected item, cluster interactions, and the small prominent-card set. Keep dense ordinary points as lightweight markers; if profiling shows sustained large visible sets or frame drops, evaluate Canvas/WebGL/data-layer rendering behind the same interaction contract. First make current viewport/zoom/filter inputs and marker lifecycle single-source and profile representative phone hardware. | Canvas/WebGL migration can improve scale but makes rich HTML interactions and accessibility harder, adds SDK/implementation complexity, and may not benefit the current neighborhood-sized data volume. Avoid an SDK rewrite without profiling. |
| Marker accessibility and touch targets | Leaflet’s reference exposes keyboard operability, `title`/`alt` for accessible labels and focus auto-pan; its accessibility guide says markers should have unique descriptive labels. WCAG AA 2.5.8 allows 24px target or spacing/essential-map exceptions; map-coordinate pins may qualify as essential, but equivalent list access is encouraged. | Labeling and keyboard access let users discover/select places without precise touch; a list gives an alternative to dense geographic targets. | Custom marker and cluster accessibility is inconsistent; some icons lack meaningful labels/keyboard contract (UXM-12). Small pin geometry is 36×44px and cluster 42×42px in reported samples, with no guaranteed expanded hit area (UXM-07). | Nonvisual users may not know place names/counts; touch selection can be difficult where points are dense. | Give each marker a business-name and category label, clusters a count and activation behavior, and ensure focus/Enter works for ordinary, selected and cluster markers. Provide equivalent list rows and use larger practical touch hit areas where this does not falsify pin geography. | Enlarging geographic hit areas causes overlapping targets and ambiguous taps; preserve coordinate correctness and route dense selection through cluster/list. |

## Product-specific recommendation order

1. Consolidate zoom, eligibility, culling and clustering around one settled viewport state; preserve the current useful card/dot/cluster progression and selected-marker exception (BHV-01, UXM-07).
2. Repair search context and scope: keep the query/scope after a choice, resolve zone mismatch visibly, and provide a synchronized mobile result tray (BHV-02/03; UXM-03/06).
3. Make active filters and count visible, and keep filter actions above the mobile navigation at 360×640 (UXM-01/05).
4. Resolve duplicate selected surfaces and define whether an excluded selection remains as a separately labeled context card (UXM-06; I17).
5. Add an explicit “search this area” control only when the directory actually fetches new data for changed bounds; current local culling does not warrant the extra action.
6. Profile before moving dense rendering to Canvas/WebGL; meanwhile improve marker labeling, alternatives and tests for pin reconciliation (UXM-12/13; BHV §4).
